1. Uvod i opis projekta

PoolBuddy je full-stack veb aplikacija za upravljanje terminima plivanja i rezervacijama u gradskom bazenu. Cilj projekta je omogućiti korisnicima da online pregledaju dostupne termine, rezervišu mesta i upravljaju sopstvenim rezervacijama, dok administrator ima potpunu kontrolu nad raspoređivanjem termina, korisnicima i CMS sadržajem sajta.

Aplikacija podržava tri tipa korisnika sa različitim nivoima pristupa:

  • Posetilac — pregleda javne stranice, registruje nalog, prijavljuje se
  • Korisnik — rezerviše termine, otkazuje rezervacije, menja profil
  • Administrator — kreira/menja/otkazuje termine, upravlja korisnicima i CMS stranicama

6. Funkcionalni opis modula

6.1 Autentifikacija (auth)

Sistem koristi JWT dual-token strategiju: kratkotrajan access token (15 minuta) i dugotrajan refresh token (7 dana) sa rotacijom pri svakoj upotrebi.

  • Registracija — korisnik unosi ime, prezime, email, telefon i lozinku. Email mora biti jedinstven. Lozinka se heši bcrypt algoritmom (10 rundi) pre čuvanja.
  • Prijava — validira se email i lozinka, a zatim se izdaje par tokena. Refresh token se čuva u localStorage (heš u bazi), access token samo u React state-u.
  • Obnova tokena — pri pokretanju aplikacije i pri svakom 401 odgovoru, frontend automatski šalje refresh token i dobija novi par. Stari refresh token se opoziva (token rotation). Race condition pri konkurentnim pozivima rešen je mutex queue mehanizmom u AuthContext i dodavanjem jti (UUID) klajma u svaki refresh token.
  • Odjavljivanje — refresh token se opoziva na serveru (postavljanje revoked_at), access token i localStorage se brišu na frontendu.

6.2 Korisnici (users)

  • Pregled profila — prijavljeni korisnik vidi sve sopstvene podatke.
  • Izmena kontakt podataka — mogu se menjati ime, prezime, email i telefon. Proverava se da novi email nije zauzet. Lozinka se menja odvojenom akcijom.
  • Promena lozinke — korisnik unosi staru lozinku (verifikuje se bcrypt-om) i novu lozinku sa potvrdom.
  • Admin: lista korisnika — administrator vidi sve korisnike sa statusom naloga.
  • Admin: aktivacija/deaktivacija — administrator može da deaktivira korisnički nalog. Administrator ne može da deaktivira sopstveni nalog.

6.3 Termini (sessions)

  • Pregled slobodnih termina (korisnik) — prikazuju se samo otvoreni termini koji nisu prošli i imaju slobodnih mesta. Dostupan filter po datumu (od / do).
  • Admin: lista svih termina — tabela svih termina uključujući otkazane, sa brojem aktivnih rezervacija.
  • Admin: kreiranje termina — unose se datum, vreme početka, vreme kraja (mora biti posle početka) i kapacitet. Validacija na tri nivoa: frontend (Zod + React Hook Form), backend (Zod middleware) i baza (BEFORE INSERT okidač).
  • Admin: izmena termina — isti podaci kao pri kreiranju, moguće samo za otvorene termine.
  • Admin: otkazivanje termina — status termina se menja na cancelled, a sve aktivne rezervacije tog termina se kaskadno menjaju na cancelled_by_admin unutar jedne SQL transakcije.
  • Admin: brisanje termina — moguće samo ako termin nema aktivnih rezervacija.
  • Admin: pregled rezervacija po terminu — lista korisnika sa statusom rezervacije i vremenom rezervacije.

6.4 Rezervacije (reservations)

  • Kreiranje rezervacije — korisnik rezerviše termin. Sistem proverava: termin postoji, status je 'open', termin nije prošao, ima slobodnih mesta, korisnik nema aktivnu rezervaciju za isti termin. Ako postoji otkazana rezervacija za isti termin, reaktivira se (UPDATE) umesto INSERT-a, čime se poštuje unique ograničenje.
  • Pregled mojih rezervacija — korisnik vidi sve sopstvene rezervacije podeljene u aktivne i otkazane, sa statusom termina i vremenima.
  • Otkazivanje rezervacije — moguće samo za aktivne rezervacije budućih termina. Proverava se vlasništvo (403 ako pokušava drugi korisnik). Status se menja na cancelled_by_user.

6.5 CMS stranice (pages)

  • Javne stranice (bez prijave) — lista objavljenih stranica sortirana po sort_order, i prikaz pojedinačne stranice po slug-u. HTML sadržaj se renderuje direktno.
  • Admin: lista svih stranica — prikazuje i objavljene i skrivene stranice.
  • Admin: kreiranje / izmena stranice — unose se naslov, slug (mora biti u formatu mala-slova-sa-crticom i jedinstven), HTML sadržaj, redosled i status objave.
  • Admin: promena statusa objave — klikom na status badge u tabeli, stranica se trenutno objavljuje ili skriva bez otvaranja modala.
  • Admin: brisanje stranice — potvrda pre brisanja.

7. API referenca

Sve rute imaju prefiks /api/v1. Zahtevi i odgovori su u JSON formatu. Greške vraćaju { "message": "..." } sa odgovarajućim HTTP statusom.

Autentifikacija: zaštićene rute zahtevaju Authorization: Bearer <access_token> zaglavlje. Admin rute zahtevaju i ulogu role = 'admin'.

POST /auth/refresh Obnova tokena. Telo: refresh_token. Vraća novi par tokena, opoziva stari javno

8. Bezbednost

Autentifikacija i tokeni

MehanizamDetalji
Access token (JWT) HS256, važi 15 minuta. Čuva se isključivo u React state (ne u localStorage/cookie) — nedostupan XSS napadima. Sadrži: userId, role, firstName, lastName.
Refresh token (JWT) HS256 + jedinstveni jti (UUID v4) klajm, važi 7 dana. Čuva se u localStorage. U bazi se čuva samo SHA-256 heš — kompromitovana baza ne otkriva tokene.
Token rotacija Pri svakom obnavljanju, stari refresh token se opoziva i izdaje novi par. Sprečava ponovnu upotrebu ukradenog tokena.
Lozinke bcrypt, 10 rundi soli. Nikada se ne čuvaju u čistom tekstu.
Deaktivacija naloga Deaktiviran korisnik ne može da se prijavi ni da obnovi token (proverava se is_active u oba toka).

Zaštita API-ja

MehanizamDetalji
Rate limiting Auth rute ograničene na 20 zahteva / 15 minuta po IP adresi (express-rate-limit). Sprečava brute-force napade na login i refresh endpointe.
Autorizacija po ulozi authenticate middleware verifikuje JWT. requireRole('admin') middleware blokira pristup admin rutama za obične korisnike (403).
SQL injection Svi upiti koriste parametrizovane prepared statements (pool.execute('... WHERE id = ?', [id])). Direktna konkatenacija stringova nigde nije prisutna.
CORS Dozvoljeni origin se definiše kroz CORS_ORIGIN environment varijablu.
Vlasništvo nad resursima Korisnik može otkazati samo sopstvenu rezervaciju. Pokušaj pristupa tuđoj vraća 403.
Mutex za refresh Axios response interceptor koristi queue mehanizam: ako je refresh već u toku, sledeći 401 čeka umesto da šalje drugi identičan zahtev. Rešava race condition koji je prouzrokovao DB unique constraint grešku.

Validacija (trostruki sloj)

  1. Frontend — React Hook Form + Zod šeme: klijentska validacija pre slanja zahteva
  2. Backend — Zod middleware (validate(schema)): server-side validacija tela zahteva pre ulaska u service sloj
  3. Baza podataka — FK ograničenja, ENUM tipovi, BEFORE INSERT okidači (npr. provjera da end_time > start_time)

Zaštita ruta

  • ProtectedRoute — prikazuje sadržaj samo ako je korisnik prijavljen; inače redirect na /login
  • AdminRoute — prikazuje sadržaj samo za korisnike sa ulogom admin; inače 403 ekran
  • Dok traje inicijalni tihi refresh (obnova sesije pri učitavanju stranice), ProtectedRoute prikazuje prazan ekran umesto redirecta — sprečava lažni logout

Upravljanje auth stanjem (AuthContext)

  • Access token čuvan u React state-u i useRef-u — ref omogućava da Axios interceptor uvek čita najnoviji token bez čekanja na re-render
  • Axios request interceptor registruje se jednom pri montiranju i čita token iz ref-a
  • Axios response interceptor hvata 401 odgovore, automatski poziva refresh i ponovo šalje originalni zahtev sa novim tokenom
  • Mount-time tihi refresh (obnova sesije) koordiniran sa interceptorom kroz zajednički isRefreshingRef mutex
